# 模式 05：集成与固定语义下的性能改动

适用：已有代码整合、归一化/数据接口连接、有具体瓶颈的局部实现变化。
性能不是自动改成 native/GPU/parallel 的理由，集成也不自动重跑全部历史实验。

## 五项交接的本次差异

1. 目标：`<哪个调用链/实测瓶颈>` 应达到 `<已选行为或预算>`。
2. 路径：指定入口、调用/消费者和 shared boundary；写明现有 checkout 与起始改动。
3. 语义：原 numerical/RNG/ordering/serialization/比较边界，允许改变的精确部分。
4. 验收：受影响边界的 focused checks；具体性能问题另给范围有限的测量方法。
5. 边界：限定 source surface 与执行上限；不换科学问题、少做工作或扩大系统结构。

## L1 增量

说明 ownership、shape、生命周期与可变共享状态；复用既有原语。当前性比较按声明 source
内容，不以 unrelated doc commit 的身份变化判定失败。保留不重叠的工作和证据。

## L2 增量

列现有完整路径及改动位置，具体说明哪部分保持原顺序/副作用、哪部分替换。
性能测量必须覆盖问题有关的真实工作；局部速度不代表完整调用完成时间。
若需要改变原任务禁止的 dtype、拓扑或科学含义，返回该具体差异，不偷偷改变合同。

## L3 增量

引用该模块现成的正确调用/转换片段，与当前改动配一个小数据例子；通用并行框架不作为
默认范例。本版以任务绑定的已有代码引用为例子，待具体题包冻结后选择。
