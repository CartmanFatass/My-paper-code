# 模式 04：runner 接线、计数和发布路径

适用：固定方法的 CLI 参数、Config、输出元数据、readback、publication 修复与技术收集。
纯收集任务不假装是编码题；它可以作为连续流程中有真实注意力要求的杂务。

## 五项交接的本次差异

1. 目标：`<调用/既有输出缺陷>` 改为 `<可核实完整产物>`。
2. 路径：明确 runner、被调用函数、writer/reader、必要测试及证据所有权。
3. 语义：参数进入实际计算而非只写 JSON；科学计数、预算和结果范围引用原卡。
4. 验收：从实际受影响入口到消费者的 focused fixture；失败/部分产物与完成状态一致。
5. 边界：不新增科学 invocation、重试、恢复系统、通用 schema/registry 或额外强制门槛。

## L1 增量

列出适用的 argv/Config/函数参数/输出字段，保留已有默认值和文件消费者预期。
说明 wall 的起止边界以及是否含初始化、学习、评估和发布；CPU work 与 elapsed 不能混用。
只记录任务要求的资源项，缺少可选资源信息不自动否定科学结果。

## L2 增量

用一个输入逐层追到实际模型/环境/学习调用再追到 published summary。
缺文件、子进程完成、wrapper 成功和完整结果要分别判断。publication 修复用 retained
fixture 或允许的非科学检查覆盖相关路径；不为了“试一下”重新训练。

## L3 增量

优先引用该方向已有最小 writer/reader 片段及一个匿名输入输出示例；新例子不应变成第二个
完整 runner。源片段和适用版本随任务固定，不复制其他对象的 counts/seed/run root。
本版不提供一个“适用于所有方向”的发布函数，因为输出契约不同。
