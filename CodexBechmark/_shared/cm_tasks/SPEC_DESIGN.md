# 主研究：RL 工程 spec 的颗粒度与复用

Owner 澄清（2026-09-09 PDT）：spec 颗粒度、delegation 指令详细度和常见任务代码范例是
本测试的重点；模型组合用于检验这些设计在不同执行者上是否仍有价值。

期望产出是“什么任务需要写清什么、哪些可以引用、哪些不值得逐次重写”的可用工作方法，
而不是只得出哪个模型便宜。现有两个场景保留：委派 spec 为主实验，CM 直接实现组为基线和
架构对照。生产角色暂不改动；候选模板可供审阅，但尚不能称为已验证的最佳默认。

## 要分别识别的三件事

1. **内容到哪一层**：L0 当前交接；L1 加任务具体工程约定；L2 加执行逻辑；L3 加代码范例。
2. **内容怎么复用**：每次完整撰写，或引用版本固定的任务模板/范例并只写本次差异。
3. **谁能用好它**：先固定 CM、implementer、reviewer 比较前两项；再用不同模型验证迁移。

“更长”不是处理定义。L2 必须增加操作与状态关系，L3 必须增加有适用条件的代码示例；
复制一页通用规范仍只是冗长。所有档位保留相同科学事实、目标、验收、预算与权限。
不得把不可缺少的语义从低档删掉，再证明高档更好。

## 分为稳定模式和任务差异

一次交接仍是已有五项，不引入新审批表。CM 根据任务选一个相关模式，填本次差异即可：

| 保留在公共模式中 | 每次任务必须明确或精确引用 |
| --- | --- |
| 该类任务的接口/状态问题，常见实现顺序，局部范例和反例 | 实际文件/入口、已有行为与要求的变化 |
| 哪些语义不能从函数名或算法名猜出 | 本任务已选定的 reward、时钟、mask、归约/梯度等适用事实 |
| 如何用最少的反例验证该类问题 | 本次需要的公开检查、最终可观察结果 |
| 该模式适用的条件、与常见相似问题的区别 | 当前 shape/单位/seed/结束条件，以及与模式不同的地方 |
| 只读引用和版本 | 所属路径、交接对象、预算与停止条件 |

未知语义不能用范例的值补齐。先从已有卡/代码恢复；只有实际意义或授权冲突才返回原
负责人。普通方法选择由执行者完成。不要求每题填写所有可能的 RL 字段。
同一保护事实只写一次或引用一次，避免模板与本次差异相互矛盾。

## 第一批任务模式

| 模式 | 覆盖的重复任务 | 应重点检验的信息 | 候选来源 |
| --- | --- | --- | --- |
| [loss / credit](patterns/01_loss_and_credit.md) | actor loss、critic target、mask、参数/权重进入学习路径 | 样本单位、归约分母、梯度路径、更新顺序 | UCOPE、RCLE、CBSC |
| [时间 / 状态](patterns/02_time_and_state.md) | termination、truncation、hold、RNN 与实体生命周期 | 哪个时钟、何时重置、谁继续、final observation | FOLR、UCOPE、SCDMP |
| [RNG / evaluation](patterns/03_rng_evaluation.md) | seed 透传、训练评估隔离、必要 checkpoint 状态 | 随机流归属、命名空间、模型状态、reporting identity | DISH、UCOPE、RCLE |
| [runner / publication](patterns/04_runner_publication.md) | CLI/Config 接线、计数、输出、失败后的发布修复 | 配置是否进入实际计算、完整与部分结果、计量起止 | 多方向 runner/collection |
| [集成 / 受限性能](patterns/05_integration_performance.md) | 跨模块集成、固定语义下局部效率改动 | 兼容面、未变科学含义、完整路径与有界检查 | UCOPE integration、CRTO/MGTAP 候选 |

这些模式来源于人工初筛及实际代码边界，不是已完成工作频率的统计结论。
本批提供三个可执行微例子说明易混淆处；它们是参考材料，不是新的 RL 框架或全任务解答。
范例旁必须写适用条件和不适用条件，防止“复用”变成不看任务直接复制。

## 主实验顺序

先固定 Astra/medium CM、Terra/high implementer、Astra/high reviewer（计划配置，未运行）。
对同一连续流程比较四档内容 × 两种交付方式，共 8 个 spec 策略：

- `fresh`：CM 逐次撰写本次完整交接，不由主持者免费提供高档定制方案。
- `reuse`：CM 引用该档允许的固定模式/范例，仅补本次差异。L0 仅复用五项交接结构，
  L1/L2/L3 才分别获得对应增量；不能通过公共目录把 L3 信息泄给 L0。

共同的任务源码、原科学卡和必要事实始终可得。`fresh` 是无新增模式库的当前工作方式，
不是禁止查原任务规范。所有组使用相同职责和裁判。
再加一个当前 CM 直接实现 + reviewer 基线，首轮共 9 次流程，而非先铺满模型组合。
筛选最多两个 spec 策略，在两个未见任务流程各做两次重复；直接基线同样复验，最多 12 次。
因此主研究计划为最多 21 次团队流程，另列协议校准与可选上下文诊断。

主研究之后，只对入围 spec 增加 Astra/medium、Luna/max implementer，检验是否降低对强
执行者的依赖；CM/reviewer 模型组合也放在扩展阶段。扩展的模型优劣仍需自己的留出验证，
不能仅借用 Terra 上的 spec 结论。完整配置见 [_host/MATRIX.json](_host/MATRIX.json)。

每次流程是同一 CM 持续完成 2–3 个代码目标及杂务。筛选与留出包含共同任务模式但来自
不同具体任务；模式在留出前冻结。这样检验跨任务适用性，又避免拿同一 bug 改名冒充泛化。
在本次重复任务中记录首次引用、再次引用以及为例外所作的改写。具体流程见
[_host/EPISODES.md](_host/EPISODES.md)。

## 除了结果，还评 spec 本身

在隐藏验收结束后，独立裁判检查：关键事实是否完整可访问、引用是否可达、说明是否
引入错误、模板假设是否适用、指令是否与卡/代码冲突、范例是否被机械误用。
区别“缺少事实”和“事实存在但执行者忽略”。CM 没按所分配档位写足信息也保留原组结果，
另报策略遵循情况；不能事后换标签美化档位效果。

同时观察 implementer 追问、CM 澄清/接管、review 发现、前序约束遗失与未完成工作。
只有团队最终质量相当，才能把更低成本解释为改进。详尽但错误的 spec 可以让多个模型
更一致地做错；它应是清晰可见的失败。

## 首次成本和复用成本分开

模式/范例首次制作与维护记为公共准备成本；每次任务查阅、选择、填差异、解释、纠错属于
实际 CM 团队成本。逐次撰写模式中 CM 的详细逻辑和范例生成完全计入该次。
报告三种账：单次原始全链成本；库首次投入；在实际已观察复用次数下的摊销成本。
对未来复用次数的推算只能是情景估计，并说明适用任务比例、版本失效和维护成本。
不能把本次 Root 写的模板当免费，也不能把今天的 131 个历史 CM 会话当作未来复用次数。

最终形成每个任务模式的建议：默认哪档、什么缺口才加细、哪些范例可用、哪些差异必须
每次写，以及适合的执行模型范围。运行前这些建议都只是候选。只有验证通过的条目再提出
具体工作流改动；不会因为 benchmark 目录多了一份模板就让生产 CM 自动加载全部材料。
