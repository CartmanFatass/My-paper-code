## 首轮三个流程

| 流程 | 来源与选取范围 | 连续编码目标 | 杂务/迟到消息 | 主要保留条件 |
| --- | --- | --- | --- | --- |
| S1：FOLR 筛选 | public lifecycle CM；从环境/collection 接口到发布路径与后续 timing 工作选有界片段 | 生命周期边界实现；同类新增事件/continuation 变体；发布路径或参数接线 | 独立 review 返回、旧 run 完成回执、只改文档的提交、owner 状态询问 | 出生/离开状态正确；先前修复不被后续小改覆盖；完整交付 |
| H1：UCOPE 留出 | p47 CM 长期复用链；选择 credit/RNG 边界与后来 seed/summary 接线，避免完整重跑研究史 | 有界策略/回报边界修复；评估不扰动训练状态；新 seed/报告连接 | 相似 run 名、8601/8602 迟到回执、邻接文件无关修改、缺失产物更正 | 训练/评估状态分离；新旧身份不串；条件与下一责任人保留 |
| H2：RCLE 留出 | actor100 CM；权重实现、readback 修复、seed20 连接的同会话链 | 参数进入实际 actor loss；输出读取/发布修复；seed 贯穿指定链 | 旧失败日志、部分收集、正确 terminal 回执、恢复与 Git 记录 | 真实计算与 metadata 一致；未完整材料不冒充完整验收；预算不漂移 |

这些是从真实工作重建的测试流程，范围会在题包冻结时具体到函数与输入；不是给 CM
三个完整科研项目。每流程尽量取 2–3 个可在有限工程检查内验收的目标，保留真实依赖。
若某来源无法构成独立、可重复的题包，用已筛选的 DISH seed 传播、ACVC recurrence/
optimizer 边界、CBSC critic target 或 UCOPE integration 替换，并在任何候选运行前冻结。
留出题的目标、缺陷和解法不能在筛选中泄露。

为测 spec 复用，题包要包含同类模式的再次应用和一次不同模式的切换。复用题共享的是
适用概念，不是同一 patch 改名。留出至少包含一个“名称相似但模式假设不同”的明确任务，
如任务内生终止与持续任务外部截断；必要事实在所有档位都给出，观察是否机械套用范例。
模板在留出前冻结，不能按留出答案补提示。尚未冻结的具体变体以题包记录为准。

## 一条流程的固定外部投递骨架

| 次序/边界 | 主持事件 | CM 应完成的可观察工作（不是标准实现答案） |
| --- | --- | --- |
| 01 开始 | 初始授权、源码、验收、现有待办/前一 run 信息 | 接手第一编码目标，建立自己需要的工作记录 |
| 02 定位后 | 邻接文件存在无关修改，提供可核实 diff | 继续改所属代码，保护无关工作 |
| 03 首次检查后 | 前一 run 的迟到回执与小型证据包 | 对齐正确身份；保留当前编码任务 |
| 04 review 边界 | 调用真实团队 reviewer；固定事件只给状态询问 | 回答状态后处理真实 review，继续而不等待额外许可 |
| 05 第一次交付后 | 第二个具体修复目标与新的症状/公开 fixture | 复用相关工作，实施修复，保持先前语义 |
| 06 第二次检查后 | 文档提交/修正回执替代旧记录 | 区分源码变化与文档变化，更新事实 |
| 07 第二次验收后 | 第三个参数/接口连接目标（如题包只含两目标则省略） | 完成透传与必要检查，不把旧值带入新结果 |
| 08 最终交付前 | 检查待收材料，其中一个声明和产物有差别 | 基于实际文件完成收尾或给出准确未完成项 |

未完成前一编码目标时仍记录后续事件，但保留依赖：不能伪造成功后跳过前置工作。
预算到达后正常返回未完成事项和已有产物，按失败结束本次，不因重开会话擦掉历史。
任务失败不导致 hosts 临时改成更容易的下一个问题。

真实 review 不按这张表编造；它可以在不同组发现不同问题并引发不同数量的修复。
固定迟到回执仅服务背景任务，不能替本次候选代码出具通过证明。代码质量另由统一裁判判定。

## 历史事实与构造的界限

同一 CM 复用、代码边界、review/执行/收集事件来自 census 所列历史指针。
投递次序、跨事件间距压缩、无关文件补丁和状态询问是为可比较而构造的测试条件。
任何新增缺陷必须标明 synthetic，不能写成历史原本发生；不改变任务的验收事实。
不加入随机大文本制造压力，使用需要实际阅读或查阅的代码、检查结果、diff 和证据。

## 小批次执行顺序

1. 制作/核验 S1、H1、H2 题包；参考实现只给主持者。检查必须能拒绝典型错误并接受正确实现。
2. 一个当前基线流程用于协议校准；如修题，升级版本并保留记录，校准不进胜率。
3. 固定 CM/implementer/reviewer，在 S1 比较 L0–L3 × fresh/reuse 共 8 个 spec 策略；
   加一个当前 CM 直接实现基线，共 9 次团队流程。详见 [主研究](../SPEC_DESIGN.md)。
4. 最多两个 spec 策略加直接实现基线，在 H1/H2 各做两次独立重复，共最多 12 次留出流程。
5. spec 入围后再扩展模型：两个策略 × 两个新增 implementer 配置，最多 4 次探索流程；
   CM 模型扩展 2 次、reviewer 组合最多 4 次，均为另选范围。扩展探索本身不能代替留出验证。
6. 需要解释上下文问题时再做预先选定交接点的 warm/cold 配对诊断；单列成本。

主研究最多 21 次团队流程，模型探索最多另 10 次，不含协议校准与可选诊断。这是设计的
分阶段范围，不是费用估计；尚无一次模型试跑。实施时先用校准实际成本冻结每阶段
token/时间/美元参考上限，再执行当时选定范围。未测 Sol、未进入阶段的配置和未测重复
均保持“未运行”。不凭一个筛选流程宣称总体最佳，也不把 21 次当作 21 个独立任务家族。
