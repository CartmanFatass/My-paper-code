# Equal DM coordination

OWNER_DIRECT: DMs are independent peers. The central Clerk role is retired. Each Astra/max DM
owns direction innovation, ordinary research execution, implementation, review intake, reports,
accepted main integration and cleanup, and applies conforming Portfolio direction decisions. Root is the user entry and shared-control engineering owner.
Portfolio owns final direction-level interpretation and delegated vacancy selection; direction
Pro is an independent scientific Reviewer. Independent Luna/high browser Transport returns directly to authors.
There is no coordinator approval, mandatory receipt hop or DM hierarchy.


Portfolio authority: docs/project/PORTFOLIO_DECISION_PROTOCOL.md now controls direction-level
CONTINUE/RECAST/PARK/CLOSE/reopening. DM owns innovation, experiments, reports and ordinary
in-scope execution, and submits lifecycle recommendations to Portfolio. No unilateral DM PARK,
slot release or archival pending that decision. Existing references to DM lifecycle management
mean proposal, reporting and execution, not final interpretation. Web Portfolio must receive and
read the protocol's fixed repository context; local conversation/skill inheritance is not assumed.

## One shared coupling record

C:/Projects/HMASD/.codex/hmasd-dm-sessions.toml is the single authoritative mutable record for
DM endpoints, direction occupancy, pending capacity requests/reservations, their accountable DM,
main writer and unresolved cross-direction handoffs. .codex/hmasd-transport.toml and compute.toml
remain service configuration, not duplicate scheduling ledgers. Cards/intakes contain science;
PORTFOLIO.md is a derived user report, never a second source of permission or pending state.
Each DM updates its own row and the shared fields it actually owns. Preserve other rows. Record
actual producer, next action and event/revision; do not call an intention running or a record applied.
Current canonical controls can be read from main regardless of direction checkout age.

## Shared writes without a standing manager

Direction authoring remains in each DM's existing branch/checkout. DMs may change needed code,
tests/adapters/dependencies there; owned paths prevent overlapping writes, not per-file authority.
Independent review and scientific constraints still apply. Committed/pushed direction revisions
can proceed to review/remote admission/launch without waiting for main integration.

Serialize actual main index/registry transactions using the same Windows named mutex
Local\HMASD_Main_Transaction. Acquire it in the process performing the complete read/edit/Git
transaction and release in finally. Read fresh HEAD/status and registry after acquisition. Never
hold it across browser generation, experiments, model reasoning or waits for another task.
Before overlapping changes, contact the recorded live main_writer directly; only that writer
releases its unfinished transaction. A stale written owner is reconciled against actual Git/task
state; do not steal an unresolved merge or commit another author's staged files. No timeout
creates permission. Root follows the same rule for shared control edits.

Each DM integrates its named accepted commits with explicit paths after checking what is already
present. Resolve semantic conflicts with the affected peer directly. Retain unmerged work and
publish the blocker/owner in the same registry while independent work proceeds. Do not manufacture
a central integration task. Update main_writer/turn for the actual transaction, and clear it on
release. Shared policy edits remain Root-owned; direction engineering needs no Root permission.

## Vacancy ownership and PARK

Target remains three occupied plus reserved direction slots, subject to actual owner changes and
resource admission. A fourth-slot stop does not suppress replacement below three. A scientific
PARK is Portfolio's decision on the DM's reasoned report, never a failed support estimate, ended object or missing ACK.
Write PARK.md with reasons, alternatives, lessons, contrary evidence, reusable assets, claim limits
and reopening conditions. Preserve and hand over accepted producers before releasing occupancy.

The departing DM owns the resulting vacancy transaction until it transfers that named transaction
to an available peer or completes it. Scientific PARK does not require continuing experiments.
For an orphan vacancy an active DM may claim it in the shared record under the short transaction
mutex; first recorded claim wins. Record request ID, author DM, reservation and next action before
Send/task creation. Others read/reuse that claim rather than create another request. A pending
Portfolio conversation stays with its author, not whichever DM has most recently become idle.

The claiming DM asks Portfolio through independent browser Transport for selection using latest
PARK/intake knowledge, full evidence accessible to Portfolio and current resource/owner constraints.
The relevant direction DM directly discusses scientific disagreements. Portfolio must address the
actual PARK rationale and explain a useful changed objective/judgment; no mandatory novelty, new
customer or positive pilot. Preserve exact question, full answer and DM response. Unchanged advice
is not a reason to create another request or another DM. Reuse/unarchive existing DMs for existing
directions. Only genuinely new/unrecoverable directions need new independent Astra/max tasks.
Before task creation recount occupied/reserved slots and record the reservation; never dispatch
both a replacement and a resurrected DM into the same slot. Selected continuation includes actual
object design/execution, not another approval or re-entry-only ticket. Other global changes retain
explicit owner scope. Do not silently change an affected peer's science or lifecycle.

A DM may archive its own task after records/evidence are committed, live producers are secured and
its outstanding coupling work has an explicit accepting peer or is complete. Send a direct App
handoff to that peer before ending; final alone is not delivery. No routine Root notification.

## Events and mechanical services

DMs send actionable App messages only to the affected peer or Transport, with request/event ID,
evidence, actual decision, next owner/action and dependency. No broadcast ACKs, periodic status
loops or obligatory message on every commit. The receiving DM completes consequences and
records them; delivery is not acceptance. No need to ask Root for ordinary repair, coordination,
implementation, new bounded objects or lifecycle choices. Escalate only an actual user choice
outside delegation or required shared policy change, with concrete source and choice.

The independent Transport observes concurrent Pro requests and archives full answers directly to
the assigning DM. Native monitors and code specialists keep their direct parent routes and
existing batch rules. Neither service consumes a direction slot or interprets scientific authority.
No heartbeat is claimed active unless actually configured; absent automation is not monitoring.
