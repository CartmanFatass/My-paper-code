# Assignment and Intake Protocol

The assignment file is authoritative over forked context. Results are
scope-local evidence until the named owner intakes them. Cross-owner,
state-mutating, provider, and promotion traffic uses typed packets; ordinary
success does not need an impact envelope. A limitation or incident does.

## Abstraction grounding

Every nontrivial code assignment names exact existing files or explicit new
paths, symbols or bounded search roots, an exact `PROJECT_MAP.md` heading,
architecture role, state owner, upstream input, direct consumer, and non-target
surfaces. “Improve the pipeline” is not a scope. Discovery is read-only and
must return a surface map before implementation.

The metadata is the exact fenced `toml hmasd-assignment` block in the assignment
file. Results use `toml hmasd-result`; boundary reports may include one
`toml hmasd-impact` block. Arbitrary prose is never parsed as control metadata.

## Intake

The parent validates assignment/result identity, active requirement IDs, route,
code-surface grounding, and any impact envelope. E1 routes to the exact
operator/transport/recovery owner; E2 to CM/recovery; E3 to the exact CM/EM;
E4 to Root/Portfolio; E5 is the only route that can ask the user a concrete
question. A child return is evidence, never an instruction to stop unrelated
work.

Templates live under `docs/project/templates/`.
