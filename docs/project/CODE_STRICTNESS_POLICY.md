# Code Strictness Profiles

Profiles describe evidence and ownership, not a universal ceremony.

| Profile | Typical scope | Required evidence |
|---|---|---|
| `R0_NAVIGATION_AND_MECHANICAL` | navigation, generated index, bounded move | smallest edit and one focused check; no reviewer or manifest |
| `R1_ROUTINE_ENGINEERING` | bug fix, CLI parameter, fixture, adapter | assignment-local design and focused tests; CM intake |
| `R2_EXPERIMENT_EXECUTION` | stepping, rollout, learner, runner, native/parallel route | manifest, resource preflight, benchmark, CM acceptance; no silent fallback |
| `R3_PROTECTED_SCIENTIFIC_SEMANTICS` | reward, gradients, lifecycle, replay, treatment/comparator | EM-owned object, exact revision, CM conformance; ambiguity returns to EM |
| `R4_CONTROL_PLANE_AND_AUTHORITY` | identity, workflow, promotion, ACL, durability | deterministic transitions, negative tests, idempotency, independent focused review |

Evidence classes `A`, `B`, and `C` refine the amount and provenance of evidence
inside a profile; they do not turn a toy exploration into conclusion-bearing
ceremony. Conversely, control-plane authority edits cannot be accepted as
routine prose. A toy file edit must not inherit formal ceremony, and a
state/authority mutation must not be treated as a routine edit.
