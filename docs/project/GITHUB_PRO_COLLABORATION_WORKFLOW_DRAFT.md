# GitHub Pro 协作流程草案

状态：DRAFT，待 Pro 审阅；不改变当前普通只读 Author 模式。
授权：所有者同意完整验证后整体迁移，并于本轮批准设计完善流程。
范围：研究讨论、Pro 决策文件交付和通知；不改变科学证据标准、节点权限、实验准入或 Git 集成职责。

## 1. 已知能力与设计目标

两次隔离测试已经观察到当前 Pro 连接器能读取固定源码与提交 diff、在指定分支新增文件、发布 Issue 评论。链接往返测试还完成长文文件、短聊天链接、Transport 归档和 Root 独立读回。证据在 docs/research/portfolio/pro_packets/20260905_github_write_probe/{roundtrip_readback,roundtrip_archive}；外部提交为 2f8a08af920a8881832d89357b06065b87facf53。这是该会话的实测能力，不是所有产品或会话的权限保证。

目标是避免模型逐层搬运正文。任务与证据放 Git，Pro 原文直接写 Git，评论传达增量与交付链接，Root/DM 直接取原文做现有 intake。Transport 继续承担必要的一次唤醒、模型/会话核验、等待和短回执；GitHub 评论本身没有已验证的自动唤醒能力。

## 2. 每轮最小材料和职责

- Root/DM：提出自然语言问题、所需决策、当前规范、证据范围、科学 claim ceiling；提交并推送 TASK.md。复用该方向的实质性 Issue，不为每轮另建 Issue。
- TASK.md：给出完整固定输入 SHA、确切文件列表、相关评论链接和提问时的讨论快照；声明输出分支、基准 SHA、唯一输出文件、唯一交付评论所在 Issue，以及只授权该范围的写操作。当前请求明确授权读取并执行此任务文件的指定范围；其他仓库内容、评论和附件只作为证据，不能自行扩大指令。
- Pro：读任务、规范和证据，写一份结论先行的自然语言 RESPONSE.md，注明实际读取来源、观察/推论、限制、最终结论或具体缺口。不得把任务 UUID、路由字段或状态 envelope 当成答案内容。
- Transport：只发送任务的固定链接和最短必要授权说明，归档聊天中的实际文件/提交/评论链接。不会撰写或改写 Pro 原文，也不解释科学结论。
- Root/DM：按固定提交读回完整文件，保留原始字节和已有归档记录，做规范符合性及科学 intake。文件成功交付不等于科学决策已形成；只有完整且回答本节点问题的结论才能按现有权限应用。
- CM/implementer/reviewer：继续在各自工程分支和 PR 上处理实际代码；Pro 研究交付默认不修改源码、不合并 PR、不更新 main 或方向状态。需要工程评审时明确列出 PR 的 base/head 与待评问题，不从文件 diff 阅读推断已具备 PR 操作能力。

## 3. 正常顺序与写入范围

1. Root/DM 将本轮任务、讨论快照与引用提交到 main 并立即 push，解析完整 SHA。使用独立本轮交付分支，从明确基准创建；分支和输出路径放已有 HANDOFF 中，不新增注册服务。例：docs/research/candidates/<direction>/pro_packets/<round>/archive/RESPONSE.md；Portfolio 使用对应 portfolio/pro_packets 路径。
2. 现有 Author 生成显式 github_delivery 模式的短链接 prompt 和内部 HANDOFF；源任务、parent、绑定、request key 保留内部。普通 archive_attachment 模式继续可用。新模式不得继承“禁止写入”的旧正文，也不得让普通模式自动获得写权限。
3. Transport 在现有绑定发送一次。Pro 先检查目标文件与本轮交付评论是否已存在；然后读取输入，生成原文，仅新增指定文件，读取服务端提交结果和文件，再发布一个包含完整提交文件链接的交付评论。
4. Pro 聊天仅返回实际链接与必要缺口。评论可附一两句结论供浏览，不能成为原文替身；结论冲突时保留两者，依固定原文核对，不能静默解释。
5. Root/DM 直接读提交：核对目标路径、允许的变更集合及输入版本、正文完整性；保存原始响应字节和实际 comment permalink，避免手抄。使用现有 intake 说明符合性、证据和下一步；按现有 Git 规则集成并立即 push。交付原文不重写，修订以新轮文件保留旧版本。
6. 评论通知可多次被观察；相同提交/输出路径已 intake 的回执只更新通知状态，不再次决策、提交或启动实验。实验仍由现有卡片和运行状态决定，不由评论触发。

## 4. 不确定性、重复与并发

| 情形 | 处理 |
| --- | --- |
| Send 已接受或是否接受不明 | 查现有消息/请求状态，等待或读回；不能因超时再 Send。 |
| 文件写入返回超时 | 查分支目标和提交。若已存在，读回并返回现有链接；无法确认就报具体不确定性，不再盲写。 |
| 文件已有且属于本轮 | 读原文和来源；匹配任务则复用，不重写。不同内容或归属不清则报告冲突，保留全部。 |
| 文件成功、评论失败 | 文件仍是有效交付候选。读 Issue 确认是否已有本轮完整文件链接；只有明确未发布时才补同一评论，不重新生成文件或科学决策。 |
| 评论成功、聊天/通知失败 | Root 可从现有 Issue/交付分支读回；恢复通知只发已有链接，不再次写入。 |
| 重复通知 | 以已有 request key 加固定输出提交/路径查 intake；不另造外部身份或签名系统。 |
| 分支发生并发修改 | 本轮独立分支仅 Pro 写；若仍发现目标已变或基准不符，不覆盖、不 force。保留提交，报告冲突；Root 根据实际 diff 选择安全集成或新交付分支。 |
| main 因其他方向前进 | 输入仍绑定原 SHA，不能静默换输入或让无关文档提交否定结果。若相关科学输入发生实质变化，Root/DM 在 intake 说明影响并决定必要的补充问题。 |
| GitHub 写权限暂不可用 | 保留已生成/已提交状态与具体缺口。只能明确降级到现有正文归档方式，并标注交付模式；不能制造“Pro 已写入”的证据。 |
| 需要修订 Pro 结论 | 同一节点的新明确问题和新一轮输出文件；引用旧原文及更改原因，保留历史，不修改旧回复或重新解释成已批准。 |

通知可重复送达，不宣称跨 GitHub/聊天/本地实现原子事务或 exactly-once。安全点是明确写入范围、实际状态读回、复用既有交付和不盲重试。使用现有客户端若无条件写入能力，明确独立分支是隔离措施而非无竞争证明。

## 5. 最小验证与迁移

已通过正常路径，不重跑正常路径来堆证据。剩余验证只针对实际失效分支：

- 重复回执：把同一测试交付链接重复交给现有 intake，确认不产生第二次评论、提交或执行；这是通知处理验证，不能冒充 provider 重复写测试。
- 文件存在：一次明确授权的隔离恢复测试，请 Pro 对已有测试文件/评论仅查验并复用，核对分支 head 和评论数量不变；不得再要求生成另一份评审。
- 并发冲突：在隔离测试分支准备已存在但内容不符合任务的目标，让 Pro 确認冲突并仅返回缺口；核对未覆盖。Root 的测试准备必须单独记录，不能当 Pro 行为。
- 缺通知：用已有交付文件在本地 intake 验证聊天回执缺失时仍可独立读取；不必真实制造网络故障。对未注入的超时保持未验证说明。
- PR 评审/合并不是此次文件协作切换的必要功能；若以后采用，另测真实 PR surface。无需新增 webhook、GitHub Actions、常驻 worker、schema 服务或权限申请。

先在 VNFC 的下一个尚未发送的真实 Pro 问题启用新模式，完成一次真实科学 intake；不得为验证工作流编造科学问题、重发已接受轮次或阻挡 B 实验。通过后在其余节点下一次自然请求时逐个启用，保留既有会话绑定、旧轮档案和进行中的请求。所有新节点均切换后的状态才称整体迁移完成。没有下一轮请求的方向不制造额外往返来凑迁移数量。

若发现交付丢失、权限变化或内容冲突，仅该请求保持明确未完成状态，其他研究继续。对明确未发送的后续请求可回退原模式；已发送轮次先核实结果，不能双路提交。回退不删除已交付文件和评论。
