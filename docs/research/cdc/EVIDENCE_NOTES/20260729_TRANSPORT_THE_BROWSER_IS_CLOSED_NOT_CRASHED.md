# 传输为什么反复被 block：浏览器是被正常关掉的，不是崩溃

两轮传输在同一处失败：Pro 的回答已经生成完毕，捕获却拿不到。本文记录实测证据，
并**更正**第 4 轮当时的诊断——那一条是错的。

## 实测

```text
last_boot            2026-07-27 10:15:52     连续运行 38.3 小时
Kernel-Power 42/107  近 8 小时内 0 条        没有休眠、没有唤醒
msedge.exe           C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe
                     150.0.4078.105，二进制最后写入 2026-07-26 12:17
                     ——会话期间没有更新过，排除「更新触发重启」
chrome.exe           App Paths 未注册
Edge Preferences     exit_type = Normal
                     profile 与 Local State 最后写入 2026-07-28 23:20:51
```

`exit_type = Normal` 是决定性的一条：Edge 是**干净退出**的。崩溃会写 `Crashed`，
被强杀会写 `SessionEnded`。所以不是崩溃、不是内存耗尽、不是休眠、不是更新。
**是有人（或某个东西）把它正常关掉了。**

## 更正：第 4 轮说「Chrome 从这台机器上消失了」，那是错的

当时的记录写：`chrome.exe` 在 Program Files、Program Files (x86)、LOCALAPPDATA、
HKLM App Paths、开始菜单以及所有 Google 目录下都找不到，因此推断「Chrome 要么装在
非标准位置，要么被中途卸载」。

**这台机器上根本没装 Chrome，从来就没有。** 承载标签页的一直是 Edge。
`tabs_context_mcp` 报的是 `chrome://newtab/`——Chromium 内核的 Edge 就是用 `chrome://`
这个 scheme——我照着这个字符串去找 `chrome.exe`，找不到，于是得出了一个关于「浏览器被
卸载」的结论。找错了可执行文件，却把「没找到」当成了「不存在」。

同一类错误今天又犯了一次：用 `"$env:ProgramFiles(x86)\..."` 去测 Edge 路径，
PowerShell 不这样展开这个变量名，于是「Edge 也不存在」。正确写法是
`${env:ProgramFiles(x86)}`，改对之后一次就找到了。

**一次失败的查找不是一条不存在的证据。** 在把「找不到」升级成「没有」之前，先证明
查找本身是对的。

## 两种故障戴着同一张面具

`screenshot` 和 `find` 超时，`javascript_tool` 却照常返回——这个组合出现过两次，
但原因不是同一个：

| | 标签页被切到后台 | 浏览器正在退出 |
|---|---|---|
| 进程 | 健在（实测 `msedge=20`） | 随后归零 |
| `visibilityState` | `hidden` | `hidden` |
| 截图 / `find` | 超时（渲染节流） | 超时 |
| `javascript_tool` | 正常 | 短暂正常 |
| 剪贴板复制 | 静默失败 | 静默失败 |
| 处置 | 激活标签页 | 会话内无解 |

第 5 轮两种都遇到了，中间隔着二十多分钟，而我把后一次当成了前一次的延续。
`document.visibilityState` 单独一项**分辨不了**这两者——必须和进程存活一起看，
并且看它会不会自行恢复。

## 死亡都发生在等待窗口里

两轮的时间形状一样：围栏发出去 → Pro 生成十几分钟 → 期间我只是 `sleep` → 回来发现
浏览器没了。第 4 轮如此，第 5 轮也如此（9 分钟 + 10 分钟两段静默）。

活跃操作期间浏览器一次都没死过。

`exit_type=Normal` 加上这个时间形状，最省事的解释是：**在这些长静默窗口里，浏览器被
外部关掉了**——这是一台共享的机器。我无法归因到具体是谁，也不需要归因，因为缓解措施
对两种情况都成立。

## 缓解，按有效性排序

1. **生成一停就先落一份临时捕获**（已写入 `$hmasd-review-round`）。一次
   `javascript_tool` 调用，不需要剪贴板、不需要焦点、后台标签页也能跑。这一条直接
   取消了「浏览器必须活到捕获完成」这个依赖，是唯一真正解决问题的一条。
2. **别一睡十分钟。** 每 2–3 分钟做一次轻量读取。这样浏览器一死就在几分钟内被发现，
   而不是二十分钟后；如果消失和空闲有关，保持接触本身也可能有用。
3. **永远不要关掉最后一个标签页。** Skill 的「先关后建」在只剩一个标签页时会连窗口
   一起关掉，从而结束整个浏览器进程。两次「The browser is shutting down」都出现在
   `tabs_close_mcp` 调用上。它不是死因——两次的超时都**早于**关闭调用——但它把一个
   可能还能救的状态变成了一个救不回来的状态。先建后关。
4. **诊断卡死之前，先同时看 `visibilityState` 与进程存活。** 任何一项单独都会骗人。
