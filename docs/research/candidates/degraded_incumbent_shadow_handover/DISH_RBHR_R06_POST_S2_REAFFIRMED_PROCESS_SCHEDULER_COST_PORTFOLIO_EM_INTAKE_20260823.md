## Conclusion

**gross architecture and feasibility decomposition** for a real isolated-
process scheduler. It is not an adequate **post-S2 residual forward price**
for the current bytes, so Portfolio should not use it unchanged as a new
implementation envelope.

Portfolio should authorize one narrower, read-only and result-blind
**current-byte residual cost and resource rebase**. The rebase must reconcile
the accepted S1/S2 work with the process design, replace the assessment's now-
invalid resource input, and return a low/central/high forward delta. Until
that return exists, neither a finite process-repair envelope nor a no-current

This is a new bounded Portfolio assessment decision, not final allocation.

## Why the reaffirmed assessment is informative but insufficient

The owner assessment already specifies the right engineering class: at most
eight worker **processes**, one isolated Python/PyTorch runtime and one total
core per worker, block-arm job ownership, dependency-aware downstream work,
deterministic global commit, and same-identity failure recovery. Its five work
families—scheduler `6/10/16`, atomic coordination `4/7/12`, acceptance
`5/8/13`, remeasurement `3/5/8`, and request preparation `1/2/3`—therefore
remain useful as a gross scope map. A second generic process-architecture
study would add little.

Two decision-critical facts prevent treating that map as the current forward
cap.

First, the assessment freezes a `7.324149699998088`-second persistent update
as its resource-model input and explicitly requires re-estimation if that
measurement changes materially. S2 later measured
`10.672341100056656` seconds on the actual thread path, a 45.7% increase. A
mechanical sensitivity substitution—not accepted process measurement—moves
the assessment's projected complete wall from `35.90/46.11/63.29` hours to
approximately `50.90/64.88/88.05` hours and projected CPU from below the
320-hour ordinary target to approximately `390.85/409.82/455.36` core-hours.
Those values remain below the unchanged 110-wall-hour and 560-core-hour hard
ceilings, but they change the ordinary-versus-hard resource case and show that
the old projection cannot carry a new resource decision. The rebase must
determine whether the S2 single-update value is a transferable process-model
input, a thread-substrate artifact, or a bounded range driver. This intake
does not make that technical determination.

Second, the assessment predates the exact post-S2 byte state. S1 and stopped
S2 consumed 20 scope-accounted engineer-days. Some resulting job-graph,
ordering, journal, receipt, acceptance-seam or measurement work may remain
usable; thread-pool, thread-lifecycle or contention-specific work may need
replacement. The assessment's `55–65%` reuse statement instead describes
prospective reuse of its central process implementation/coordination **within
DISH**. It is not a measured salvage fraction for the S1/S2 bytes and cannot
be applied as a discount.

The 20 historical days are sunk evidence, not a future authorization. Adding
all 20 to `19/32/52` would double count surviving work; subtracting 20, or
applying the `55–65%` figure, would credit thread-specific work without an
owner audit and could underprice the process replacement. Operational Root's
reaffirmation faithfully preserves the earlier owner return but, because it
performed no new assessment, it resolves neither issue.
