## Conclusion

The exact r05 object is statically single-valued and is technically bindable,
observable and capable of literal invariant-in-free containment. No
science-bearing implementation choice remains for EM clarification. The
repository does **not** contain a conforming PCPI r05 package, production
backend registration, exact-numeric trainer, exhaustive evaluator or manifest
lifecycle. Those are missing engineering substrate, not scientific defects.

The incorporated public-law source is present at the registered immutable
bytes: static SHA-256 inspection of
`VNFC_TARGET_EXCLUSIVE_POST_CHURN_RECOVERY_SCIENCE_CARD.md` returned
`be15c98e59e2e8b95bccc51e00c755d943627cc59e482c136892809ab717fe64`,
equal to the binding. Existing BPCR r09 code supplies useful design patterns
for a source-keyed C++ batch loader, physical host, write-once lifecycle and
blinded frontier, but it is not a literal r05 implementation and must not be
adapted in place. In particular, BPCR uses a different scorer width and
parameter inventory, a different normal law, a different optimizer/objective,
rank-based serialization and no PCPI presentation matrix or exhaustive
commutation trace.

The prospective construction burden is material: **137/246/424 experienced-
engineer days** (low/central/high). A typical complete CPU-only object is
statically projected at **128/416/1,420 CPU core-hours** and **30/75/260 wall

## Literal comparator, containment and matched-work feasibility

Literal containment is feasible. Both arms can share one parameter schema,
allocate every tensor including complete `P`, execute the same tensor
construction, scorer calls, full-batch objective, backward pass, scalar
optimizer traversal, checkpoint and trace schemas, and differ only by frozen
`alpha=0` versus `alpha=1`. The containment embedding copies every homologous
byte and zeros exactly the eight first-layer columns multiplying the residual
half of `c_j`; it does not delete `P`, skip residual construction or reduce
work. The trained-free projected clone is a separate evaluation view that
retains every parameter byte and zeros only the runtime residual half of
`c_j`.

Prospective TEST-only proof seams required before any scientific identity are:

1. parameter-inventory and byte-copy proof, including the exact eight-column
   zero map and no other changed byte;
2. invariant-arm versus embedded-free bitwise equality of scores, masks,
   conditionals and physical command for all supported widths and prefix forms;
3. strictness witness with two unequal slot residuals and one nonzero residual
   column reversing the same physical candidates' odds;
4. compiled logical-work counters proving both arms execute identical encoder,
   `P`, residual, scorer, reduction, loss, backward, optimizer and checkpoint
   operations;
5. permutation transport/inverse-map round trips for every `N` and malformed,
   duplicate and missing-key rejection;
6. public-tag/`CHOICE_SIGNATURE` diversity receipts that cannot substitute for
   stable-key command equality;
7. FEATURE-FLIP and ROW-SWAP timing/field-diff proofs;
8. free projected-clone common-prefix total-variation and complete-command
   separation; and
9. widths `1/8/32/128` plus worker counts `1/4/8` with identical logical
   outputs, order-independent worker scheduling and one common source identity.

Widths are prospective engineering candidates, not a universal matrix and not
an authorization. Final widths must be selected by result-blind measurement.

## Native-first production architecture

The smallest coherent prospective split is:

```text
vnfc_pcpi_r05_contract
  immutable inputs, schemas, dimensions, logical counts, branch law
vnfc_pcpi_r05_counter_numeric
  SHA/R64/rejection, inverse-normal, strict binary64, QR, exp/log/sqrt
vnfc_pcpi_r05_physics_generator
  public-law simulation, legal commands, attempts, state/pair registration
vnfc_pcpi_r05_tensor_model
  public tensor ABI, encoders, P/control, scorer, teacher-forced CE/backward
vnfc_pcpi_r05_optimizer
  exact scalar clipping and AdamW traversal/serialization
vnfc_pcpi_r05_evaluator
  permutations, inverse map, ordinary/matched prefixes, interventions, traces
vnfc_pcpi_r05_analyzer
  completeness, competence/sensitivity/commutation/activity, seven branches
vnfc_pcpi_r05_lifecycle
  source-keyed loader, atomic ledgers/checkpoints/chunks/manifests and resume
python_oracle_and_lifecycle_only
  deterministic fixtures/reference checks, build/load glue and metadata audit
```

The first production-capable state generator, physical simulation, legal
decoder, exhaustive evaluator, intervention engine, trace encoder and analyzer
must be C++ batched. Python may provide only an oracle, fixture adapter,
source-keyed load glue and lifecycle orchestration; it may not own scalar
state/presentation/decoder/trace loops or be a production fallback.

The safest exact route is CPU C++ with one thread per worker and independent
workers partitioned by replicate/arm/evaluation unit. Address generation is
order-free, but accepted ledgers and terminal indexes commit in registered
lexicographic order. Parallel scheduling must never enter a counter address,
reduction, tensor, command, checkpoint or result. Training reductions and the
scalar AdamW recurrence remain serial in their registered scalar order inside
each replicate-arm; parallelism is across independent replicate-arm units.

A PyTorch forward/backward/optimizer route is **not statically accepted**.
Existing BPCR code calls framework softmax/autograd/AdamW and does not prove the
r05 correctly rounded elementary functions, no-contraction scalar order or
exact parameter trajectory. It could be admitted later only if a custom
binary64 implementation proves byte-identical gradients and all 256 parameter
snapshots against the registered scalar law. The same fence applies more
strongly to GPU kernels. No credible accelerator production route exists from
current repository evidence.

The native ABI should use fixed-width little-/big-endian fields exactly where
the card specifies, explicit record sizes/version, and no caller-selected
source/build root. The cache key must cover all native sources, immutable card
and public-law bytes, compiler identity/flags, numeric-library identity and ABI
schema. Correct-rounding mode, disabled contraction and elementary-function
identity are source-manifest facts. Checkpoint, trace and terminal publication
use same-directory temporary files, fsync, no-overwrite atomic rename and
append-only chunk indexes. Resume validates every source/coordinate/master/
logical-frontier binding before loading model bytes.

### RSS, storage and I/O

At prospective widths `1/8/32/128`, peak per one-thread worker is estimated at
**1/2/4 GiB** (low/central/high), dominated by native model/trace buffers and
compression. Eight workers therefore require **8/16/32 GiB** aggregate RSS;
the high-risk envelope allowing unusually large trace chunks is **8 GiB per
worker / 64 GiB aggregate**. Sixteen workers are not assumed because they may
double aggregate RSS and saturate storage without reducing registered scalar
work.

The trace projection uses the explicit formula
`1,983,744 presentations * 14/32/64 KiB per complete ordinary+matched trace`,
or approximately **26.5/60.5/121.1 GiB** uncompressed presentation traces.
The low/central/high byte widths bracket agent-layer rows, mean/max, scores,
supports/probabilities, commands, inverse maps, prefixes and interventions;

scratch materially exceeds durable storage.

### Dependency, toolchain and licensing surface

- MSVC x64 C++20 strict floating point and Windows SDK are already used by the
  BPCR source-keyed loader, but exact r05 flags and library identities require
  new acceptance.
- SHA-256 can use a vendored permissive implementation or an OS provider only
  after byte-for-byte vector conformance and source-manifest binding.
- Standard C/C++ `exp`/`log` and inverse-normal functions do not provide the
  registered correctly-rounded guarantee. A correctly rounded implementation
  (for example a vetted permissive core or dynamically linked MPFR-class
  reference) is required; license and redistribution obligations must be
  reviewed before selection. No library choice changes the scientific value.
- Existing NumPy/PyTorch may remain TEST/oracle tooling. Their ordinary kernels
  are not a production exact-numeric substrate for this object.
- Existing zlib-style chunk compression and atomic lifecycle patterns are
  reusable after r05 schema/source reacceptance. Codec choice cannot alter
  canonical uncompressed bytes.

### Exact primitive fractions and bounded worst case

In the central typical projection, SHA/rejection and state generation are
roughly 3%, correctly rounded inverse-normal plus QR 4%, fitting (including
correctly rounded `exp`/`log`, backward and scalar AdamW) 24%, exhaustive
forward/evaluation 53%, and trace encode/read/analyze 16% of CPU. These are
unmeasured fractions.

The hard exhaustion envelope is qualitatively different. The state frontier
can inspect up to 37,748,736 attempts before the first terminal exhaustion.
The initialization frontier can consume 11,534,336 QR attempts and
58,342,768,640 correctly rounded inverse-normal values. At only 10--100
microseconds per inverse-normal value, that primitive alone is about
**162,000--1,620,000 CPUh**, before QR. Exact QR and state simulation can add
the same order or more. Therefore the frozen finite worst case is
operation-bounded but not economically bounded by the typical estimate; a
credible wall/resource ceiling requires the later primitive benchmark. This
does not authorize reducing caps or changing the object.

A compact attempt ledger need record canonical addresses, first-failure/full-
rank facts and digests rather than duplicate regenerable normal arrays. At
64--256 bytes per attempt, the hard state plus QR ledger alone is approximately
**2.9--11.7 GiB**, before accepted-state/trace content. A static-invalid
manifest stops at the first exact trigger and never trains.

### Atomic resume and ordinary interruption

Chunk-level write-once checkpoints should bound ordinary recomputation to one
replicate-arm update chunk or one evaluation chunk. With 128--1024
presentations per chunk, expected recomputation is below about **0.01--0.06%
of final evaluation** plus one chunk validation. Atomic temp duplication adds
up to one chunk and one index to scratch. A restart must rehash the source,
frontier, checkpoint and completed chunk indexes; central restart audit is
estimated at **10--40 minutes and 20--80 GiB reads**, depending on index and
chunk layout. These are unmeasured lifecycle projections.
