## 发生了什么

前两次扫查覆盖的是审计脚本与 pooler 的测试。本轮扫**审计所测量的对象**——
Scenario 7 环境本身,理由是那里的空守卫会把环境缺陷放进结果,而世界替换缺陷
(迭代 25)正是这样溜过来的、且是撞见而非查出的。

发现两条,都附"能让测试套保持全绿的生产代码变异",修复都观察过 RED。

### 1. 钳位函数在断言自己的钳位边界

`test_dynamic_return_threshold_and_service_cutoff_are_separate` 的两条断言都
不可能失败:

- `min <= x <= max` 断言的是 `np.clip(..., min, max)` 的输出落在自己的钳位
  里——**任何**钳位实现都过,包括完全无视距离的;
- `isclose(margins[0], _raw_return_energy_margins()[0])` 比的是同一公式的
  **两份手写副本**(`_update_return_energy_state` 与 `_raw_return_energy_margins`
  各自写了一遍 `battery − required − reserve`)。两边都来自代码。

变异:把阈值压成常量 `return_threshold_min`。**42/42 与 197/197 全绿。**

**够不够得到主张——我修正了自己的推理。** 起初以为它经 `−2·return_constraint_cost`
直接进 `G`;查下来不是,那一项读的是 raw margins,不是阈值。但它在 `:1908`/
`:2035` 是返航触发判定、在 `:2250` 是观测第 7 维,因此改变审计所测的轨迹与策略
所见。**间接,但真实**;按间接记录,不拔高。

修复:阈值必须**按距离判别**(远角无人机严格高于停在充电站的那架,常量无法满足,
且不需重新推导物理);margin 改由测试自己的字面量独立重算。两个 RED:
`far=0.25 near=0.25`;以及从**两份副本**同时删掉 reserve 后 `0.3830 vs 0.2830`。

### 2. 名字里写着 per-UAV,测试从未变化那一维(更重)

`test_cutoff_and_depletion_events_fire_once_per_uav` 本身构造不错——驱动真实
函数,`first==1 / repeated==0` 排除了"永远闩"和"从不闩"两种实现。**但所有断言
只驱动 UAV 0**,所以"per uav"这一维从未被检验:一个**全队共用一个标志**的闩锁
照样通过。变异后 **214/214 全绿**。

**这一条直接承载主张,而且是权重最大的项。** `compute_G` 减去
`5·new_cutoff + 10·new_depletion`。全局闩锁在**第二架**无人机越过阈值的瞬间就
开始少计——八机编队在能量压力下这是常态——于是 `G` 系统性偏高。D7.S 的窗口内
闩锁数的正是这些事件。与上一条不同,它不需要行为路径,是算术直入主量。

生产实现本身是逐机正确的(`cutoff_event_seen` 是布尔数组);只是没有东西证明它。

修复:驱动第二架,断言它的首次事件在 UAV 0 已闩的情况下仍然计数,且随后也会闩。
两个 RED:全局闩锁下 UAV 1 首次 cutoff 计为 0;完全去掉闩锁则重复断言失败——
所以这条修复不能被"取消闩锁"满足。

239 项测试绿。

## 规则更新

`$hmasd-acceptance-gate` 的配对反例规则新增两条变体:

- **永远不要断言代码结构上必然成立的后置条件**(钳位值在钳位内、已排序的表有序、
  归一化向量模为一)——读起来像性质检查,实为关于代码**形状**而非**正确性**的
  同义反复;
- **把测试自己的名字当作规格,检查其中的量词**——"once **per uav**" 只驱动一架、
  "**every** field" 只变一个字段、"across **processes**" 只在一个解释器里跑。
  这一扫最便宜,因为它只比对名字与函数体,完全不需要理解实现。

第二条大概率是后续产出最高的一扫。
