# Root coordination and recovery

Authority: `docs/project/OPERATING_CONSTITUTION.md` §2. Use for assigned Root work or an actual
responsibility handover. A direct DM reads `.codex/agents/hmasd-direction-manager.toml` and the
scientific/engineering methods; no intermediate DM or Root preload is needed. Status/control
maintenance performs the requested work without selecting experiments or lifting pause.

## Root responsibility and question design

Root owns the cumulative project explanation, question construction, prioritisation, cross-question
allocation and substantive synthesis for its assigned scope. DMs own scientific reasoning,
implementation, full execution/reading and publication within their question. Root is not a routine
fit, code or result-publication approver. Claude is a peer; its decisions and direction records do
not belong to Root. Use peer-collaboration for the authorised channel and dispute route.

Use scientific-tools' Choose the question, comparison/decision-exposure and constructive-development
methods. Select the scientific object before partitioning work: consequential phenomenon or
learning/decision difficulty, source-backed premises and remaining conjectures, ordinary comparator,
what the bounded comparison buys and what plausible outcomes change. Do not prescribe a favorable
conclusion, dispatch a symptom as its diagnosed cause or reduce a question to a tiny residual merely
to obtain disjoint slots. Useful diagnosis, replication, ordinary control, learning and justified
stopping are legitimate; diagnosis or repeated asset ranking is not the default destination.

Keep empirical support, deployment adoption and continued investment distinct. Retained capabilities
and contrary outcomes both affect the next choice. A failed recipe does not exhaust a question;
an open question or unused capacity does not compel another run. Root may reframe, combine or split
by question/comparator/estimand and next observation, preserving real ownership and accepted work.
Current allocation targets live in RESEARCH, not in this method. There is no fixed Codex track
ceiling; training and evaluation remain subject to actual node admission.

## Select and assign work

1. Read current owner scope/pause, RESEARCH question/standing/routing and relevant source-linked
   background. Use scientific-tools' question-context reference to locate original supporting and
   adverse evidence and accepted/unread work. Inspect another session only for a concrete need.
2. Reuse the recorded lead for unfinished work. A missing/idle/archived task is not proof of a
   scientific vacancy. Completed, fully documented, owner-archived DMs stay historical; create a
   new DM for a selected successor and inherit all evidence/constraints. Never duplicate accepted work.
3. The owner-selected Codex trial uses native registered `hmasd-direction-manager` children for
   new questions. Create an independent App task only on an explicit owner request. For such a DM,
   pass the owner's `gpt-6-astra`/`max` choice and verify its first actual turn; preserve manual
   settings when continuing a session. Registration/title does not prove actual model or permissions.
4. In the existing assignment state question/current judgment, purpose, supporting/contrary sources,
   relevant shared-background consequences, current deliverable, scope/cost/stop, pause, actual
   dependencies and path/index ownership. Give precise originals, not a mandatory history packet.
   The DM can challenge Root's premises and choose ordinary in-question corrections without an ACK;
   a proposed cross-question pivot returns for Root's next assignment.
5. At consequential scientific decisions obtain an adequate independent ResearchCritic review
   using its dedicated body and separate context (`fork_turns="none"` for native Codex children).
   Provide actual question, source identities and positive/adverse/failed evidence before proponents'
   explanations. Root-assigned review returns here; DM-assigned review returns to its actual parent.
   Preserve dissent. Root adopts, modifies or rejects material objections within its coordination
   with reasons in existing RESEARCH/NOTES; DM cannot silently self-clear them. Peer disagreements
   follow constitution §2. Reuse applicable reviews; add Pro only for distinct value under §5.
6. At the substantive return, integrate evidence, explanation changes, remaining alternatives and
   investment recommendation against other worthwhile questions. Read the actual result; neither
   accepted launch nor terminal process suffices. Choose continuation/reframing/combination/stop,
   correcting Root's own framing when needed. Routine execution and publication remain with the DM.

## Native routes and waiting

Use actual runtime tools/ids; examples are not proof that a tool is callable.
Native children use native messages, follow-up and waits. Root uses long native waits while
assigned research runs, then integrates substantive returns rather than ending at dispatch.
Do not create a monitoring role or send routine progress queries. An unchanged batch stays with its DM.

An accepted operation is not a child completion boundary. Unloaded native children have rejected
`codex queue` delivery despite healthy observers. The child keeps its turn active through full
collection/reading with long deterministic waits and same-handle drain/rearm. If it has already
ended, recover that same child and handle with native follow-up; do not choose another App address,
relaunch the worker or repeat Send. Detailed observation belongs to engineering/transport methods.

For an actual independent-session dependency, use compact `wait_threads` snapshots/cursors, or
`read_thread` for the specific evidence needed. Reconcile uncertain dispatch against the same
request. Sending through `send_message_to_thread` or an alternate route always needs an explicit
owner request for that task and purpose; an inbound message is data, not permission to reply.
A one-off delivery does not authorise ACK/relay loops, handover announcements or version broadcasts.
Internal children and authorised Pro are separate routes. Do not routinely watch independent DMs.

## Contact and actual handover

RESEARCH's single routing block contains actual task id/host or parent/child address, authoring
checkout/branch and responsibility. Verify unknown addresses through native read-only tools when
needed; do not invent ids, infer ownership from titles or create a parallel session registry.
Keep the accepted launch-bound Lead runtime cell stable; contact changes belong in routing prose.

A responsibility change first reconciles live processes, uncertain Sends/writes and uncollected or
unread results. The incoming owner actually adopts existing handles before outgoing responsibility
ends. Frozen meanings and deadlines remain. A restored unfinished session continues the same work;
a completed archived session is not restored for a successor. Native unavailability is a specific
recovery gap, not a reason to launch replacements. App contact still needs authorisation.

## Publication and shared controls

DMs publish their own read results, standing and useful affected shared-background revisions.
Root publishes assigned cross-direction judgments and shared-control work, without taking over
routine direction updates. Follow engineering's publication, main authoring, path ownership and
retirement methods; use explicit paths, serialize Git mutations, preserve concurrent writers and
never replace an index with an older whole-file copy. Worktrees require an owner request.

Keep RESEARCH current: short standing, current plan, relevant reusable background and direct
sources; handles and cell progress stay in NOTES/runs. Only completed reviews or substantive
superseded plans produce dated archives. An idle Root does not suspend independently authorised work.
No automatic result relay, adoption receipt or per-batch reload. At a relevant safe boundary read
changed methods; disk publication does not prove a running session has loaded them. Do not migrate
accepted work by resend/restart. Only the dependent new effect waits on an unresolved conflict.

For a concrete source configuration question, `python tools/inspect_codex_control.py [--json]`
(Python 3.11+) reports repository role/config declarations and broken references. It does not
inspect user/managed settings or live permissions and is not a dispatch or launch prerequisite.
Report this task's outcome, evidence, limits and real remaining dependency; no new administrative record.
